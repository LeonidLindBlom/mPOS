# mPOS ControlSys — архитектура и каналы связи

## Общее

* Центральная сущность `controlsys.ControlSys` запускается внутри KasperskyOS CE (QEMU, образ `build/einit/kos-qemu-image`).
* Автозапуск конфигурируется через `einit/src/init.yaml.in`; безопасность — `einit/src/security.psl.in`.
* Доменные сервисы ControlSys разбиты по `controlsys/src/core/*` и подключаются к state-machine через `include/controlsys/services/*`.

## Канал событий (виртуальный UART → TCP)

1. **Аппаратная сторона.** К каждому запуску QEMU добавляется дополнительный последовательный порт:

   ```
   -chardev socket,id=eventbus,host=${CONTROL_SYS_EVENT_HOST:-127.0.0.1},port=${CONTROL_SYS_EVENT_PORT:-28090},server=on,wait=off \
   -serial chardev:eventbus
   ```

   Настройка лежит в `einit/CMakeLists.txt` (переменные `CONTROL_SYS_EVENT_PORT`, `CONTROL_SYS_EVENT_HOST`, `CONTROL_SYS_QEMU_HOSTFWD`). По умолчанию слушаем `127.0.0.1:28090`, но переменные можно переопределить перед запуском `cmake --build ... --target sim`.

2. **Гостевая сторона.** ControlSys пытается открыть `/dev/ttyAMA1` → `/dev/ttyAMA2` → `/dev/ttyS1` → `/dev/ttyS2` (можно задать путь через `CTL_EVENT_TTY`). Успешное открытие означает, что все события читаются из UART; если открыть не удалось, модуль падает обратно на stdin (как раньше).

3. **Хостовая сторона.** Любой клиент (скрипты из `scripts/test_events`, `nc`, произвольный Python) может подключиться к `tcp://<host>:28090`, передать строку JSON и закрыть соединение. Строки должны завершаться `\n`. Параллельные подключения обслуживаются последовательно (chardev позволяет только одно соединение одновременно).

4. **Fallback.** Если UART недоступен или порт занят, ControlSys продолжает работать: встроенный сценарий отрабатывает один цикл, а дальше state-machine остаётся в фоне и ждёт, пока UART откроется (например, когда `event_sender.py` подключится повторно). Для полного отключения UART можно установить `CTL_EVENT_TTY=/dev/stdin`.

> **Демо-режим.** На время отладки доменов внешний канал отключён: `state_machine.c` проигрывает готовые сценарии (`event_script.c`) и не читает UART. Чтобы вернуться к внешним событиям, восстановите вызовы `ctl_event_channel_init/next` в `sm_run_demo()`.

Диаграмма потока:

```
test scripts (input/card/net) --TCP--> QEMU chardev (port 28090)
                                     |
                                 virt serial (ttyAMA1)
                                     |
                            ControlSys event_channel
```

## Проброс сетевых портов

* `CONTROL_SYS_QEMU_HOSTFWD` (см. `einit/CMakeLists.txt`) управляет user-net пробросами (`28080..28084`, `29090`). Эти порты пока резервируются под будущие сервисы (дисплей, принтер, netgw, банк).
* UART-порт (`CONTROL_SYS_EVENT_PORT`, по умолчанию 28090) не идёт через user-net; он публикуется прямым `-chardev socket`. Если нужно слушать на другом интерфейсе/порту, задайте переменные окружения перед сборкой/запуском.

## Документы и принятые решения

* **UART/virtio порт** — текущий основной канал внешних событий (см. раздел выше). Если в будущем заработает TCP-стек внутри KOS, переложим приём событий обратно на `kl.VfsNet`, но UART останется резервным.
* **DNet / kl.VfsNet** — включены в образ (см. `external/net_vfs`, `einit/CMakeLists.txt`), но пока драйвер не находит аппаратный сервис в QEMU → `kl.drivers.DNetSrv` падает. Решение: либо портировать virtio-net драйвер, либо продолжать использовать UART для обмена.
* **Отчёт** — любые дальнейшие изменения (новые мосты, IPC, ограничения KSS) фиксируем в этом файле, чтобы понимать, через что именно идут контролируемые каналы.

## Брокер событий (хостовый)

Для автоматизации интеграции используется скрипт `tools/event_broker.py`. Он запускает ControlSys (через `cmake --build build --target run`) и слушает TCP-порт (по умолчанию 28090). Каждый JSON, полученный от модуля, пересылается в stdin ControlSys. Таким образом:

```
test script → broker (TCP 28090) → stdin ControlSys (host binary) → state-machine
```

ControlSys читает stdin (переменная `CTL_EVENT_TTY=/dev/stdin`), поэтому никакие дополнительные UART-устройства не нужны. Для быстрой отладки в обход KOS собираем host-версию (`tools/build_host_controlsys.sh`) и запускаем через `tools/run_host_controlsys.sh`. Брокер можно расширить — например, добавив подтверждения, маршрутизацию по `target`, статистику и т.п.

## Домены безопасности ControlSys

| Домен | Ответственность | Реализация |
|-------|-----------------|------------|
| **Manager** | Оркестрация сценариев (см. PlantUML «Транзакции/Обновления/Журнал») | `state_machine.c` + `TxContext` |
| **Input Guard** | Анализ каналов Heartbeat, проверка сетевых и энергетических аномалий | `net_verifier.c`, `power_verifier.c`, `init_module.c` |
| **Card/Data Verifier** | Проверка данных карты, ПИН-переход | `card_verifier.c` |
| **Transaction Generator** | Формирование ARQC/подписание + журнал транзакций | `txn_builder.c`, `journal.c` |
| **Status Verifier** | Валидирует ответы банка, отслеживает повторы/гонки | `status_verifier.c` |
| **Output Controller** | Управляет выводом на дисплей/принтер, уведомляет пользователя | `output_controller.c` |
| **Update Chain** | Загрузчик → хранилище → верификатор → установщик | `update_loader.c`, `update_storage.c`, `update_verifier.c`, `update_installer.c` |
| **Auth & Audit** | Аутентификация оператора и контроль доступа к обновлениям/журналу | `auth_module.c`, `journal.c` |

Домены живут в отдельных единицах трансляции (KOS-субъекты можно разнести позже, заменив прямые вызовы на NK IPC). Manager взаимодействует с ними строго по интерфейсам из `include/controlsys/services/*`, что позволяет переупаковать каждый сервис в отдельный NK-домен без правок state-machine.

### Сценарии из диаграмм

- **Инициализация транзакции.** `Heartbeat` → `net_verifier`/`power_verifier`; `init_module` агрегирует результат и разрешает `SetAmount`. После разрешения `output_controller` показывает «Приложите карту», а Manager переходит к состояниям `AwaitCard/Pin`. Любое расхождение (нестабильный сигнал, скачки напряжения) блокирует старт и отображает ошибку.
- **Проведение транзакции.** `card_verifier` проверяет PAN/EMV, `output_controller` запрашивает ПИН. Ответ банка проходит через `status_verifier`, затем `txn_builder` + `journal` формируют запись и печатается чек. Верификатор статуса предотвращает повторное использование старых ответов и контролирует последовательность (`seq`, `latency`).
- **Обновление прошивки.** `update_loader` инициирует сессию только после `auth_module`. Части прошивки собираются в `update_storage`, `update_verifier` подтверждает подпись, `update_installer` применяет образ. Все этапы отражаются через `output_controller`. Этим реализована диаграмма «Процесс обновления прошивки».
- **Выгрузка журнала.** Аутентификация оператора (`auth_module`) остаётся обязательным шагом перед выдачей записей из `journal`. На текущем шаге журнал экспортируется через Manager, а сетевой модуль (`net`) будет подключён по аналогии с PlantUML.

### Отражение целей безопасности

- **ЦБ-1/ЦБ-5/ЦБ-6.** `status_verifier` + `txn_builder` обеспечивают аутентичность исхода операции: только подтверждённые ответы проходят к `output_controller` и покупателю.
- **ЦБ-2.** `journal.c` пишет неизменяемые записи; доступ защищён `auth_module` до выгрузки журнала.
- **ЦБ-3/ЦБ-4.** Обновления проходят все этапы цепочки доверия (загрузчик → хранилище → верификатор → установщик) до входа в систему, а `card_verifier` фильтрует входящие данные карты.
- **ЦБ-7.** `net_verifier`, `power_verifier` и `init_module` проверяют среду и блокируют запуск при нарушении предпосылок (см. ПБ-1/ПБ-2: доверяем банку и отсутствию физического вмешательства).

## Тестирование сквозных сценариев

1. Собрать образ: `./cross-build.sh`.
2. Запустить брокер/кос: `tools/run_kos_via_broker.sh` (лог автоматически пишется в `out.txt`).
3. Отправить эталонную последовательность событий: `EVENT_HOST=127.0.0.1 EVENT_PORT=28090 python3 scripts/test_events/event_sender.py`.
4. Негативные сценарии: измените параметры `Heartbeat` (например, `"signal":5` или `"mv":2800`) и убедитесь, что `init_module`/`output_controller` блокируют запуск; повторите `BankResponse` с меньшим `seq`, чтобы увидеть отказ `status_verifier`.

Все наблюдения (ошибки EventChannel, разрешения доменов и т.д.) автоматически попадают в `out.txt`, который прикладываем к отчёту.
